# 05 UGC 实现与技术验证

## 系统目标

先验证和平精英 / 绿洲启元 UGC 能否支撑核心玩法，不等整图完成后才发现关键系统受限。验证重点不是“能不能做出完整版本”，而是尽早确认撤离搜打、掉落、未结算物资、死亡损失、保险箱和 PVP/PVE 规则有没有不可接受的技术边界。

## 结论快照

| 模块 | 当前判断 | 依据 | 需要验证的缺口 |
| --- | --- | --- | --- |
| 怪物刷新与波次 | 可做，优先走官方怪物刷新器 | 怪物刷新器支持刷新点、刷怪策略、刷怪管理器和波次流程 | Boss/精英差异、死亡回调、多人性能 |
| 怪物掉落 | 可做，优先走通用掉落组件 | 怪物蓝图可挂 `UGCPresetCommonDropItemComponent`，死亡时服务端 `StartDrop` | 掉落归属、队伍贡献、掉落权限 |
| 场景物资刷新 | 可做，优先走物资刷新器 | 物资刷新点支持物资 ID、掉落表、掉落组表、自定义 Lua 生成 | 是否支持本项目自定义物品、拾取后状态标记 |
| 未结算背包 | 高风险，需要原型验证 | V2 背包支持持久化、仓库、扩展 UI、操作按钮 | 是否能给单件物品挂“未结算/已结算”状态并可靠持久化 |
| 死亡损失 | 可部分配置，规则需自定义 | 物品掉落与保留支持死亡保留、掉落、不生成盒子等配置 | “仅损失未结算物资、保留保险箱物资”是否能按实例区分 |
| 保险箱 | 高风险，需要替代方案 | 背包系统有仓库和槽位，死亡保留是按物品配置 | 若不能按实例保留，可改成保险箱槽位/独立虚拟仓库 |
| 撤离结算 | 可做但需并发验证 | 模式编辑器触发器、碰撞盒 Overlap、Lua 服务端逻辑可触发结算 | 多人同时进圈、重复触发、断线/死亡边界 |
| PVE/PVP 倍率 | 可做，优先走全局伤害公式 | 全局伤害公式可统一覆写最终伤害，并读取伤害上下文 | 区域识别、玩家/怪物识别、装备词条接入 |
| PVP 区域规则 | 中风险 | 队伍/阵营和全局伤害公式可做伤害过滤 | 是否能稳定判断“人在 PVP 区域内”并阻止伤害 |

## P0 技术验证

| 优先级 | 验证项 | 成功标准 | 推荐验证方式 |
| --- | --- | --- | --- |
| P0 | 怪物刷新与波次 | 能在指定区域刷新普通怪、精英和 Boss，能按波次推进 | 创建 `BP_UGCMobSpawner` 子蓝图和 `BP_UGCMobSpawnerManager` 子蓝图；用怪物组表区分普通/精英/Boss；验证 `All Mob Die` 后进入下一波 |
| P0 | 怪物死亡掉落 | 怪物死亡后按表生成掉落，且只在服务端生成一次 | 在怪物蓝图挂通用掉落组件，配置掉落表或蓝图固定掉落；在 `BPDie` 中 `HasAuthority()` 后调用 `StartDrop` |
| P0 | 掉落拾取入背包 | 掉落物可被玩家拾取并进入 V2 背包 | 启用 `GP_BackpackV2`；用物品编辑器 2.0 创建测试物品；验证 Wrapper 掉落与“直接进背包”两种模式 |
| P0 | 未结算背包 | 拾取物品默认未结算；撤离后变为已结算；下一局可在仓库看到 | 用 V2 背包持久化物品 + 自定义物品 UI/详情/按钮验证状态展示；如果实例状态不可持久化，改用“未结算背包表 + 撤离时转换为仓库物品”的方案 |
| P0 | 死亡损失 | 死亡后未结算物资按规则损失，已结算/保险箱物资保留 | 先配置物品死亡掉落属性验证保留/掉落/禁止掉落；再验证是否能按实例状态筛选，不能则按物品类型或独立容器降级 |
| P0 | 保险箱 | 保险箱物品死亡后保留，且容量有限 | 优先验证“保险箱专属物品类型/槽位 + 死亡保留”；备选为自定义 UI 管理一份服务端数据，死亡时重新发放 |
| P0 | 撤离触发器 | 多人进入撤离区后稳定结算，单人不能重复刷结算 | 用碰撞盒 `OnComponentBeginOverlap` 或模式编辑器触发器；服务端维护 `PlayerKey -> Extracting/Extracted` 状态；验证多人同时触发 |

## P1 技术验证

| 优先级 | 验证项 | 成功标准 | 推荐验证方式 |
| --- | --- | --- | --- |
| P1 | PVP 区域规则 | 指定区域内允许玩家互伤，区域外禁止或衰减玩家互伤 | 全局伤害公式读取攻击者、受害者和伤害上下文；结合区域状态表返回 0 或原伤害 |
| P1 | PVE/PVP 倍率 | 同一装备对怪物和玩家有不同伤害倍率 | 在全局伤害公式中区分受害者类型；读取装备/属性/Tag 后计算倍率 |
| P1 | Boss 掉落归属 | Boss 死亡后按小队或贡献控制开启权限 | 记录伤害贡献；Boss 死亡时生成掉落并写入可拾取白名单；若实体掉落无法控权，则改成直接发放到获奖玩家背包/仓库 |

## 最小原型顺序

1. 启用 V2 背包：确认 `GP_BackpackV2` 生效，创建 1 个可持久化测试物品。
2. 怪物刷新原型：1 个刷新点、1 个怪、1 次死亡回调。
3. 掉落原型：怪物死亡掉落 1 个测试物品，玩家拾取进入背包。
4. 死亡规则原型：测试物品配置为保留/掉落/禁止掉落，记录实际表现。
5. 撤离原型：进入撤离碰撞盒后，将本局获得物资转为仓库/已结算物资。
6. 保险箱原型：把 1 个物品放入保险箱，死亡后验证是否保留。
7. 伤害公式原型：同一武器攻击玩家和怪物，输出不同最终伤害。

## 建议数据结构草案

第一阶段如果 V2 背包实例状态难以扩展，可以先在服务端维护本局收益表：

```lua
RunLootState = {
    [PlayerKey] = {
        UnsettledItems = {
            { InstanceID = 0, ItemID = 8310001, Count = 1, Quality = 2, Protected = false },
        },
        SafeBoxItems = {
            { InstanceID = 0, ItemID = 8311001, Count = 1, Quality = 3, Protected = true },
        },
        Extracted = false,
        Dead = false,
    }
}
```

验证重点是“规则正确”，不是一开始就把所有状态塞进正式背包实例。等闭环跑通后，再决定是接 V2 背包持久化、仓库，还是用自建数据转换成已结算物品。

## 关键实现假设

- 新背包需要和物品编辑器 2.0 配套使用；旧物资编辑器和经典背包不适合作为本玩法主路径。
- “死亡损失”和“保险箱”不要先假设能按物品实例自由改规则。官方死亡掉落规则主要按物品配置生效，实例级状态必须单独验证。
- “撤离入库”优先理解为把本局临时收益转换成 V2 仓库/持久化物品，而不是让所有拾取物天然跨局保留。
- 怪物掉落、撤离结算、死亡处理都应以服务端为准，避免客户端重复触发或被多人并发打穿。

## 主要风险

- 物品实例级自定义状态不一定能直接持久化，“未结算/已结算”可能要用自建服务端表或转换物品来表达。
- 死亡掉落规则可能更适合按物品类型配置，不一定天然支持同一物品按实例状态分别掉落/保留。
- 保险箱如果做成普通背包内物品，可能难以和死亡掉落规则解耦；更稳的方向是专属槽位、专属物品类型或独立仓库数据。
- PVP 区域控制依赖伤害公式和区域状态判断，必须验证延迟、边界、复活和离区后的状态清理。
- Boss 掉落归属如果依赖地面实体白名单，风险较高；直接发放奖励到获奖玩家背包/仓库可能更稳。
